# Assumptions and Decisions

`ARCHITECTURE.md` is the source of truth for this project. Where it is ambiguous,
silent, or contradicts itself, the decisions below were taken — always the most
conservative reading that keeps documented behavior working. Each entry says what
the spec says, what the code does, and why.

## Reading the spec

| # | Topic | Spec | Decision |
|---|-------|------|----------|
| A1 | Code listings | §4–§13 show "full code" sketches. | The sketches are illustrative. Behavior described in prose, the wire-format tables, and the roadmap is authoritative. Where the existing code already deviated with a documented reason (streaming `ManifestBuilder`, `Sha256` behind a core `HasherPort`), the deviation stays. |
| A2 | Response frames | The layout tables for `CHUNK_RESPONSE` and `PIECE_MAP_RESPONSE` start with the status byte, and the `TcpPeerConnector` sketch reads the status first; the `FrameEncoder` sketch writes an extra message-type byte before it. | Responses carry **no** message-type byte. Two of the three sources agree, and the pairing is implicit on a one-request connection. |
| A3 | Status `0x02 ERROR` | Defined, never said when to send. | Sent for an unknown message type (as the sketch does) and when the server fails internally while serving (e.g. storage error), so the client fails fast and tries another peer instead of waiting for a timeout. |

## Behavior the spec leaves open

| # | Topic | Decision | Why |
|---|-------|----------|-----|
| B1 | Manifest validation | `fileHash` and every chunk `sha256` must be 64 hex characters; every chunk except the last must be exactly `chunkSize`, the last at most `chunkSize`. | §2 defines both as SHA-256 and chunks as fixed-size slices. A malformed hash could never verify, so every chunk would be downloaded and then rejected. |
| B2 | Server read timeout | Accepted sockets get a 10 s read timeout. | Mirrors the client's 10 s timeout. Without it an idle or half-open client holds a handler and a file descriptor forever. |
| B3 | Peer selection | "First peer that holds the chunk" means first **in the order the user listed peers**. | The previous code iterated a hash map, so the choice was effectively random and failures were not reproducible. |
| B4 | Nothing left to download | When resume finds every chunk already valid on disk, peers are not contacted. | Piece maps only serve to schedule downloads; a finished file should verify even with every peer offline. |
| B5 | CLI failures | A failing command prints one line, `"<command> failed: <reason>"`, to stderr and exits `1`; usage errors exit `2` (picocli default). | The §13 sketch catches every exception and exits `0`, which would make scripted downloads report success after failing. |
| B6 | Storage lifecycle | `FileChannelStorage.close()` is terminal; reads/writes afterwards throw `IllegalStateException`. Writes require `preallocateSpace()` first. | Previously a read after close silently reopened (and leaked) a channel, and a write after a read-only open failed deep inside NIO. |
| B7 | Logging | One line per record: `[LEVEL] message`. | JUL's default two-line, timestamped format buries the message in CLI output. |
| B8 | Help | Every command accepts `-h/--help`. No `--version`. | The README promised `--help`; nothing asks for a version flag. |

## Roadmap items deliberately not implemented

Implemented only where it makes sense; these were judged not to.

| Roadmap item | Reason |
|--------------|--------|
| Phase 1 — "`ManifestBuilder` chunks a byte array in memory" | A learning step that §12 already replaces with a file-based builder (and the code with a streaming one). Adding a byte-array entry point now would be an API used only by tests. |
| Phase 4 — "`AtomicReference<BitSet>` for piece map updates" | §20.2 itself says `synchronized` is the right choice here: writes are rare (once per chunk) and nothing reads the map concurrently with downloads. Copy-on-write would only add allocation. The Phase 4 guarantees (bounded in-flight downloads, CAS state transitions, no double scheduling) are verified by tests instead. |

## Packaging and process

| # | Topic | Decision |
|---|-------|----------|
| P1 | Running the CLI | The `application` plugin builds `cli/build/install/swarm-share/bin/swarm-share`. The old README command (`java -cp cli/build/classes/java/main …`) could not work: it omits every dependency. |
| P2 | Native image | GraalVM CE 25 via the official Gradle plugin. Jackson metadata comes from the GraalVM reachability-metadata repository; the manifest DTOs ship their own `reachability-metadata.json`; picocli metadata is generated by `picocli-codegen`. |
| P3 | E2E tests | One suite (`cli/src/e2eTest`) launches the packaged executable as real processes; Gradle runs it against the JVM distribution (`e2eTest`, part of `check`) and the native binary (`nativeE2eTest`). |
| P4 | Coverage | JaCoCo per module, plus `jacocoAggregatedReport` across modules (domain code is mostly exercised by other modules' tests). |
| P5 | Versions | Each roadmap milestone is a minor release (`v0.2.0`, …). The release that completes the roadmap is `v1.0.0`, matching the spec's "v1" scope (see Non-Goals). |
| P6 | Mockito | Removed: its only use was mocking value records, which `AGENTS.md` discourages; real records are simpler. |
